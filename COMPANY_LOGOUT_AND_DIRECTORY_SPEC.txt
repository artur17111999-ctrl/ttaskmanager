ТЕХНИЧЕСКОЕ ЗАДАНИЕ
Полный выход из учетной записи и корпоративные справочники
Проект: Sticky CRM
Версия: 1.0
Дата: 06.08.2026
Статус: к реализации


1. ЦЕЛЬ И ГРАНИЦЫ

Документ описывает следующий релиз Sticky CRM:

1. Полный выход пользователя из учетной записи из нижней части основного меню,
   рядом с ФИО пользователя.
2. Справочник должностей и справочник подразделений, изолированные по компаниям.
3. Использование этих справочников при создании, приглашении и редактировании
   сотрудников.
4. Защиту данных от доступа к другой компании и подготовку к серверной модели
   сессий, расширенным ролям, импортам и нескольким компаниям.

Изменения не должны менять существующие правила работы задач, чатов, стиков,
уведомлений и приглашений, кроме добавления обязательной проверки company_id и
использования новых справочников.

В рамках этого релиза не реализуются биллинг, SSO/SCIM, мобильный клиент и
платное увеличение лимита сотрудников. Для них должны быть оставлены точки
расширения.


2. ТЕРМИНЫ И РОЛИ

Компания (tenant) - изолированная область данных, которой принадлежит сотрудник.
Сотрудник - персональная запись в employees, связанная с учетной записью.
Должность - company-scoped каталог, описывающий роль сотрудника в штатной
структуре, например "Менеджер".
Подразделение - company-scoped каталог, например "Отдел продаж".
Справочник - набор активных и архивных записей соответствующего типа.
Полный выход - завершение текущей локальной сессии и отзыв ее серверной
авторизации, если серверная сессия уже используется.

Роли текущего релиза:

- system_admin - техническое администрирование, не является обычным участником
  компании;
- company_owner (admin) - владелец компании, видит раздел "Компания" и управляет
  реквизитами, справочниками и сотрудниками;
- company_admin - администратор компании, управляет сотрудниками только в рамках
  выданных разрешений; по текущему правилу раздел "Компания" ему не показывается;
- employee - обычный сотрудник без управления справочниками.

По умолчанию только company_owner может изменять реквизиты компании и
справочники. В будущем владелец сможет выдать company_admin отдельное право
company.catalog.manage без предоставления доступа к платежам и передаче
владения.


3. ФУНКЦИОНАЛЬНЫЕ ТРЕБОВАНИЯ

3.1. Полный выход из учетной записи

3.1.1. В левом основном меню под ФИО пользователя разместить компактный блок
профиля с кнопкой/действием "Выйти". Кнопка должна быть доступна с клавиатуры,
иметь понятную подпись и tooltip, не перекрывать ФИО и не менять ширину меню.

3.1.2. При нажатии показывать подтверждение:
"Выйти из учетной записи? Открытые изменения будут сохранены согласно обычным
правилам приложения." Кнопки: "Выйти" и "Отмена". Повторный клик во время
запроса блокируется.

3.1.3. Перед завершением выхода:

- остановить таймеры уведомлений и синхронизации стиков;
- прекратить фоновые запросы и дождаться безопасного завершения активной
  операции либо отменить ее с понятным сообщением;
- закрыть/скрыть дочерние окна и стики текущего пользователя, чтобы после выхода
  на экране не остались персональные данные;
- скрыть иконку и меню трея текущей сессии;
- отозвать серверную сессию (если используется таблица sessions) или увеличить
  accounts.session_generation минимум на единицу;
- очистить access_context, токены и временные данные в памяти;
- очистить сохраненные данные только текущей сессии. Разрешается оставить только
  логин, если пользователь явно включил "Запомнить логин". Пароль, токены и
  company_id в QSettings не сохранять;
- закрыть MainWindow и открыть AuthWindow в чистом состоянии.

3.1.4. После выхода старый токен, копия AccessContext или ранее открытая форма не
должны позволять выполнять запросы. Любой запрос со старым session_generation
должен завершаться общей ошибкой AuthenticationRequired.

3.1.5. Выход из одной компании в будущей multi-tenant модели не должен удалять
другие членства пользователя. Предусмотреть отдельные операции "Выйти из текущей
сессии" и "Завершить все сессии".

3.1.6. Закрытие окна крестиком и выход через трей не считаются выходом из учетной
записи: текущее поведение трея сохраняется. При выборе "Выйти" пользователь
должен быть именно разлогинен, а не только скрыт.

3.2. Раздел "Компания" и справочники

3.2.1. В разделе "Компания" добавить блок/вкладки:

- "Реквизиты компании";
- "Должности";
- "Подразделения";
- "Сотрудники" (ссылка на существующий реестр);
- "Аудит" (на первом этапе только для owner, при наличии разрешения).

3.2.2. Вкладки "Должности" и "Подразделения" показываются только после
проверки прав и наличия активной компании. Скрытие кнопки в UI не является
механизмом безопасности: каждая операция повторно проверяется в сервисном слое.

3.2.3. Должность содержит:

- id;
- company_id;
- name (обязательное, 1-150 символов после trim);
- code (необязательное, 1-32 символа, уникальное внутри компании без учета регистра);
- description (необязательное, до 1000 символов);
- sort_order (целое, по умолчанию 0);
- is_active;
- created_at, updated_at, archived_at;
- created_by, updated_by.

3.2.4. Подразделение содержит:

- id;
- company_id;
- name (обязательное, 1-150 символов после trim);
- code (необязательное, уникальное внутри компании без учета регистра);
- description (необязательное, до 1000 символов);
- parent_id (NULL в MVP; зарезервировать для иерархии подразделений);
- manager_employee_id (NULL, будущая функция);
- sort_order;
- is_active;
- created_at, updated_at, archived_at;
- created_by, updated_by.

3.2.5. Для обоих справочников реализовать:

- просмотр активных записей, поиск и сортировку;
- создание записи через диалог с валидацией до отправки;
- редактирование названия, кода, описания и порядка;
- временное архивирование и восстановление;
- запрет физического удаления записи, которая используется сотрудником,
  приглашением, задачей или отчетом;
- отображение количества связанных сотрудников;
- предупреждение перед архивированием записи с зависимостями;
- немедленное сохранение с сообщением об успехе или понятной причиной отказа;
- отмену несохраненных изменений без потери ранее сохраненных данных.

3.2.6. Архивная должность/подразделение:

- не предлагается при создании нового сотрудника и приглашения;
- остается видимой в карточке уже назначенного сотрудника;
- может быть восстановлена владельцем;
- не переименовывается автоматически при массовой операции без подтверждения.

3.2.7. В реестре сотрудников добавить фильтры по активной должности и
подразделению, отображать их название и признак архивности. При редактировании
сотрудника разрешать только записи из того же company_id.

3.2.8. В приглашении хранить идентификаторы должности и подразделения, но при
каждом просмотре и принятии повторно проверять принадлежность этих идентификаторов
компании приглашения и их активность. Нельзя принять приглашение с подмененным
position_id/department_id.

3.3. Дополнительные доработки релиза

3.3.1. Унифицировать каталог статусов задач и тегов: у каждой компании свой
набор, свой порядок, активность и аудит. Все SELECT/INSERT/UPDATE/DELETE должны
содержать server-derived company_id; пересечение компаний запрещено FK и
сервисными проверками.

3.3.2. При удалении/архивировании сотрудника сохранять исторические значения
должности и подразделения в аудите и карточках задач. История не должна зависеть
от возможности открыть текущую запись справочника.

3.3.3. Добавить единое состояние компании (active/blocked/archived): при blocked
запретить новые приглашения, создание чатов и задач; чтение и экспорт разрешать
только в соответствии с политикой owner/system_admin.

3.3.4. Добавить на страницу компании счетчики: активные сотрудники, лимит,
ожидающие приглашения, активные должности и подразделения. Лимит по умолчанию
остается 15; pending invitation учитывается как зарезервированное место, чтобы
обойти лимит конкурентными запросами было невозможно.

3.3.5. Добавить экспорт справочников в CSV только для owner с маскированием
персональных данных. Импорт реализовать позже через dry-run, отчет ошибок и
идемпотентный ключ операции.

3.3.6. Добавить журнал изменений для компании, справочников и сотрудников:
создание, изменение, архивирование, восстановление, назначение, приглашение,
выход, отзыв сессии и отказ в доступе. Секреты, пароли и токены в журнал не
попадают.


4. ЦЕЛЕВАЯ МОДЕЛЬ ДАННЫХ

4.1. Новые таблицы

company_positions:

- id BIGSERIAL PRIMARY KEY;
- company_id INTEGER NOT NULL REFERENCES companies(id) ON DELETE RESTRICT;
- name VARCHAR(150) NOT NULL;
- normalized_name VARCHAR(150) NOT NULL;
- code VARCHAR(32);
- description VARCHAR(1000);
- sort_order INTEGER NOT NULL DEFAULT 0;
- is_active BOOLEAN NOT NULL DEFAULT TRUE;
- created_at, updated_at, archived_at TIMESTAMPTZ;
- created_by, updated_by INTEGER REFERENCES employees(id) ON DELETE SET NULL.

company_departments:

- id BIGSERIAL PRIMARY KEY;
- company_id INTEGER NOT NULL REFERENCES companies(id) ON DELETE RESTRICT;
- name VARCHAR(150) NOT NULL;
- normalized_name VARCHAR(150) NOT NULL;
- code VARCHAR(32);
- description VARCHAR(1000);
- parent_id BIGINT NULL REFERENCES company_departments(id) ON DELETE RESTRICT;
- manager_employee_id INTEGER NULL;
- sort_order INTEGER NOT NULL DEFAULT 0;
- is_active BOOLEAN NOT NULL DEFAULT TRUE;
- created_at, updated_at, archived_at TIMESTAMPTZ;
- created_by, updated_by INTEGER REFERENCES employees(id) ON DELETE SET NULL.

4.2. Ограничения

- UNIQUE(company_id, normalized_name) для активных записей;
- UNIQUE(company_id, lower(code)) для непустого code;
- CHECK для длины и непустого name;
- индекс по (company_id, is_active, sort_order, name);
- composite FK для manager_employee_id: сотрудник обязан принадлежать той же
  компании;
- parent_id обязан принадлежать той же компании; циклы запрещены сервисной
  проверкой и отдельным тестом;
- удаление компании, используемого каталога или сотрудника с зависимостями только
  через архивирование либо формальный процесс миграции.

4.3. Связь сотрудников

На переходный период добавить в employees:

- company_position_id BIGINT NULL;
- company_department_id BIGINT NULL.

Новые поля ссылаются на `(id, company_id)` либо проверяются эквивалентным
composite FK. Старые `position_id` и `department_id` не удалять в первой
миграции: существующие клиенты должны продолжить чтение. После backfill и
проверки аудита переключить все записи на новые поля, запретить новые значения
старых полей, затем удалить их отдельной миграцией в будущем релизе.

Переход должен быть идемпотентным:

1. создать таблицы и колонки;
2. создать записи каталогов для каждой компании по утвержденной карте;
3. выполнить backfill employees и pending invitations;
4. запустить отчет о NULL, чужих company_id и дубликатах;
5. включить чтение/запись новых полей feature flag;
6. только после успешного аудита валидировать FK.


5. СЕРВИСНЫЙ СЛОЙ И API-КОНТРАКТ

Добавить сервисы с единым контекстом доверенного пользователя:

- list_company_positions(principal, include_archived=False, query=None);
- create_company_position(principal, payload, request_id);
- update_company_position(principal, position_id, payload, request_id);
- archive_company_position(principal, position_id, request_id);
- restore_company_position(principal, position_id, request_id);
- list_company_departments(...);
- create/update/archive/restore_company_department(...);
- logout_current_session(principal, request_id);
- logout_all_sessions(principal, request_id) - зарезервировать для следующего этапа.

Правила API:

- company_id не принимается как источник истины из UI; он берется из trusted
  session/principal;
- каждый ID ресурса проверяется через `WHERE id = ? AND company_id = ?`;
- недоступная запись возвращает единый ResourceNotFound, без раскрытия ее
  существования в другой компании;
- операции записи выполняются в транзакции;
- request_id и idempotency key обязательны для повторяемых записей;
- ошибки валидации не содержат SQL, stack trace, токен приглашения или пароль;
- журналирование выполняется в той же транзакции, что и изменение;
- после изменения возвращается актуальная версия строки и updated_at.


6. ПОЛНЫЙ LOGOUT И СЕССИИ

6.1. Минимальная реализация

- при login создается server-side session с token_hash, account_id, employee_id,
  company_id, expires_at и client metadata;
- raw token передается клиенту один раз и не записывается в БД, логи или QSettings;
- logout отзывает только текущий session_id и увеличивает generation при
  необходимости;
- при увольнении, блокировке учетной записи, блокировке компании или смене
  критической роли отзываются все сессии сотрудника;
- повторный logout идемпотентен и возвращает успешный результат;
- после logout UI очищает память, закрывает дочерние окна и не возвращается в
  MainWindow без новой аутентификации.

6.2. Будущее развитие

- список активных устройств с датой, IP в маскированном виде и последней
  активностью;
- "Завершить все остальные сессии";
- idle timeout и абсолютный срок жизни;
- MFA (TOTP/WebAuthn), recovery codes;
- refresh-token rotation для API-клиента;
- уведомление о новом входе и отзыве сессии;
- SSO/OIDC/SCIM для корпоративных планов.


7. БЕЗОПАСНОСТЬ И ИЗОЛЯЦИЯ TENANT

7.1. Авторизация

- проверять активность account, employee и company при каждом запросе;
- права owner/admin вычислять на сервере, не доверять роли из формы;
- catalog.manage отделить от employees.manage и billing.manage;
- company_admin по умолчанию не получает доступ к разделу "Компания";
- system_admin использовать только для технических операций с отдельным аудитом;
- массовые операции ограничить текущей компанией и лимитом размера запроса.

7.2. Защита БД

- параметризованные запросы, отсутствие динамического SQL из пользовательских
  строк;
- FK, CHECK, partial unique indexes и NOT NULL после backfill;
- уникальность имен без учета регистра через normalized_name;
- транзакционный advisory lock для конкурентного создания справочников и
  выделения мест сотрудников;
- запрет cross-company JOIN без явного условия company_id;
- регулярный tenant audit с blocking findings для чужих ссылок, orphan rows,
  NULL company_id и архивных записей, назначенных новым сотрудникам;
- least privilege для DB-пользователя приложения и отдельная роль миграций.

7.3. Секреты и персональные данные

- пароль PostgreSQL хранить только в pgpass/секретном хранилище вне репозитория;
- не хранить пароль Sticky CRM, raw session token и invitation token в QSettings;
- логи и audit_log очищать от секретов, паролей и полного IP при необходимости;
- email и телефоны показывать только пользователям с соответствующим правом;
- экспорт защищать повторной проверкой роли, размером, rate limit и audit-событием;
- резервные копии шифровать и регулярно проверять восстановлением.

7.4. Logout UI

- не оставлять данные в буфере обмена и временных файлах приложения;
- закрывать открытые карточки и стики после подтвержденного выхода;
- исключить автоматический повторный запрос по таймерам после logout;
- обработать обрыв сети: локально очистить сессию и показать, что серверный отзыв
  будет повторен при следующем подключении;
- не показывать разные сообщения для "сессия не существует" и "сессия чужая".


8. МИГРАЦИИ И ОБРАТНАЯ СОВМЕСТИМОСТЬ

Создать следующую миграцию после 013, например 014_company_catalogs_logout.sql:

1. создать `company_positions`, `company_departments`, индексы и ограничения;
2. добавить новые nullable FK-поля employees;
3. создать таблицу sessions, если она еще не введена, и индексы по account_id,
   token_hash, expires_at, revoked_at;
4. добавить audit event types для catalog и logout;
5. выполнить только проверяемый backfill, без автоматического удаления старых
   данных;
6. записать migration checksum через migration_runner;
7. предоставить check-only отчет до включения feature flag.

Откат:

- отключить feature flag;
- оставить новые таблицы и данные для forward-fix;
- не откатывать уже принятые приглашения и увольнения обратным UPDATE;
- при ошибке backfill восстановить backup и повторить на staging;
- удаление старых полей выполнять только в отдельном релизе после периода
  совместимости и подтверждения аудита.


9. ЭТАПЫ РЕАЛИЗАЦИИ

Этап 0. Подготовка

- зафиксировать текущую схему и миграции 010-013;
- сделать backup и restore drill;
- описать права owner/admin и матрицу доступа;
- включить feature flags `company_catalogs_v2` и `server_logout`.

Этап 1. Серверная модель logout

- таблица sessions/отзыв токенов;
- сервис logout_current_session и generation checks;
- аудит и idempotency;
- тесты повторного logout, устаревшего токена и параллельного logout.

Этап 2. Схема и сервисы каталогов

- migration 014;
- backfill и tenant audit;
- CRUD сервисы должностей/подразделений;
- composite FK и запрет назначения архивных/чужих записей;
- обновление invitation_service и company_service.

Этап 3. UI

- кнопка "Выйти" под ФИО;
- вкладки справочников в CompanyWidget;
- диалоги создания/редактирования/архивирования;
- фильтры и счетчики сотрудников;
- сохранение существующего QSS и общего стиля приложения.

Этап 4. Интеграция

- EmployeesWidget использует company-scoped каталоги;
- приглашения показывают актуальные названия и проверяют ID;
- статусы и теги задач фильтруются по компании;
- открытые формы корректно обновляются после изменения справочника.

Этап 5. Проверка и rollout

- прогнать migration_runner --check;
- выполнить messaging/tenant audit;
- smoke-тест login/logout/relogin;
- включить flags сначала для staging, затем для локального и production;
- контролировать ошибки и быстро отключить flags при регрессии.


10. ТЕСТИРОВАНИЕ И КРИТЕРИИ ПРИЕМКИ

10.1. Unit

- нормализация name/code и проверка длины;
- уникальность в одной компании и одинаковые имена в разных компаниях;
- запрет архивного каталога для нового сотрудника;
- цикл parent_id и чужой manager_employee_id;
- проверка прав owner/admin/employee;
- идемпотентность logout и catalog writes;
- отсутствие секретов в исключениях и audit payload.

10.2. Integration/DB

- миграция 014 на пустой и исторической БД;
- backfill без потери сотрудников и приглашений;
- concurrent create с одним code дает одну запись и понятную ошибку;
- cross-company position/department/task/status/tag всегда отклоняется;
- удаление компании и каталога с зависимостями блокируется;
- revoked session не принимает запросы;
- logout закрывает текущие окна и повторный login создает новый контекст.

10.3. UI

- кнопка находится внизу меню рядом с ФИО и видна только в авторизованном окне;
- подтверждение выхода, состояние загрузки и ошибка сети отображаются корректно;
- после выхода нельзя вернуться кнопкой Back/таймером в старые данные;
- справочники не растягивают карточку и поддерживают клавиатуру, фокус и
  локализацию ошибок;
- архивные строки визуально отличаются, но остаются доступными для восстановления.

10.4. Приемка

Функция считается готовой, если:

- owner создает две должности и два подразделения, назначает их сотруднику и
  видит изменения после повторного входа;
- второй компании доступны только ее записи с теми же названиями;
- employee/company_admin не могут получить чужую запись через подмену ID;
- архивная запись не предлагается новому приглашению и не теряется у текущего
  сотрудника;
- logout отзывает сессию, закрывает стики и требует новый вход;
- старые миграции и существующие задачи/чаты/стики проходят regression tests;
- tenant audit возвращает `ok: true`.


11. РИСКИ И МЕРЫ

Риск: существующие глобальные positions/departments имеют одинаковые ID у
разных компаний. Мера: новые company-scoped таблицы и переходные поля, dry-run
backfill, запрет удаления старых таблиц до завершения миграции.

Риск: logout только закрывает окно, но токен остается действительным. Мера:
server-side revoke, session_generation, тест запроса со старым токеном.

Риск: гонка при добавлении сотрудника сверх лимита. Мера: SELECT FOR UPDATE
компании и учет pending invitations в одной транзакции.

Риск: IDOR через ручную подмену position_id, department_id, task_status_id или
tag_id. Мера: company_id из trusted principal, composite FK и негативные тесты.

Риск: архивирование используемого каталога ломает историю. Мера: soft archive,
исторический snapshot названия и запрет hard delete.

Риск: секрет попадает в логи или QSettings. Мера: redaction filter, тест поиска
secret-like значений и code review изменений логирования.

Риск: старый клиент не знает новые поля. Мера: additive migrations, feature flag,
minimum client version и период обратной совместимости.

Риск: потеря данных при backfill. Мера: backup, staging restore, checksum,
отчет до/после и forward-fix вместо разрушительного rollback.


12. НАБЛЮДАЕМОСТЬ

Метрики:

- logout_success_total, logout_failed_total, logout_latency;
- active_sessions, revoked_sessions, stale_session_rejections;
- catalog_create/update/archive/restore_total;
- catalog_validation_failed_total;
- cross_company_denied_total;
- employee_seat_usage и pending_invitation_seat_usage;
- migration_duration и audit_blocking_findings.

Алерты:

- любое blocking tenant finding;
- рост отказов logout или повторных запросов по revoked token;
- попытки cross-company доступа;
- превышение лимита сотрудников;
- ошибки FK/backfill и рост deadlock retry.
