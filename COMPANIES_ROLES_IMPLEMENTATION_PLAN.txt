ПЛАН РЕАЛИЗАЦИИ МУЛЬТИКОМПАНИЙ, СОТРУДНИКОВ И РОЛЕВОЙ МОДЕЛИ

Проект: Sticky CRM
Дата подготовки: 05.08.2026
Статус документа: план реализации, кодовые изменения не выполнялись


1. ЦЕЛЬ И ГРАНИЦЫ ПРОЕКТА

Цель первого этапа:
- добавить справочник компаний;
- связать каждого сотрудника с компанией;
- добавить базовую роль сотрудника;
- добавить страницу «Сотрудники»;
- изолировать сотрудников, чаты и задачи по компаниям;
- сделать статусы задач и теги отдельными для каждой компании;
- не допустить чтение или изменение данных другой компании;
- сохранить работоспособность существующих пользователей и данных.

Ключевой принцип:
company_id является границей данных (tenant boundary). Ограничения должны работать
на уровне функций доступа к БД, а не только на уровне фильтров интерфейса.

В первый релиз не входят:
- сложный конструктор ролей и разрешений;
- биллинг компаний;
- внешние клиенты и подрядчики;
- иерархия дочерних юридических лиц;
- полноценный серверный API;
- мобильный и веб-клиент.

Под «полноценным серверным API» здесь понимается перенос всей бизнес-логики и всех
модулей. Минимальный API аутентификации и tenant-scoped операций из раздела 2.6
является обязательной частью безопасного запуска, а не отложенным развитием.


2. ОБЯЗАТЕЛЬНЫЕ РЕШЕНИЯ ДО НАЧАЛА РАЗРАБОТКИ

До реализации необходимо зафиксировать следующие правила:

2.1. Создание компаний
Рекомендуемый вариант:
- компании создаёт system_admin;
- первый администратор компании получает роль company_admin;
- остальных сотрудников добавляют по приглашению.

Не рекомендуется разрешать пользователю свободно выбирать компанию при регистрации:
это позволит присоединиться к чужой компании без подтверждения.

2.2. Базовые роли
- employee: обычный сотрудник;
- company_admin: администратор своей компании;
- system_admin: системный администратор всех компаний.

2.3. Доступ system_admin
Рекомендуется разделить:
- административный доступ к компаниям и пользователям;
- доступ к содержимому сообщений и задач.

По умолчанию system_admin не должен читать личную переписку без отдельного разрешения.

2.4. Переход сотрудника между компаниями
Рекомендуемое правило:
- исторические задачи и сообщения остаются в исходной компании;
- сотруднику меняется company_id только для новых операций;
- перед переводом должны быть переназначены активные задачи;
- старые чаты новой компании сотруднику недоступны.

2.5. Удаление компании
Физическое удаление запрещается на первом этапе.
Использовать статус active/blocked/archived и дату деактивации.

2.6. Доверенная граница аутентификации
Передаваемый desktop-клиентом actor_user_id не является доказательством личности.
Промышленный режим мультикомпаний нельзя включать, пока desktop-клиент подключается
к PostgreSQL под общими реквизитами с прямыми правами на таблицы.

Обязательный минимальный вариант до подключения второй компании:
- desktop-клиент аутентифицируется через серверный API;
- API получает employee_id и company_id из проверенной серверной сессии или токена,
  а не из параметров операции;
- прикладная роль desktop-клиента не имеет прямых SELECT/INSERT/UPDATE/DELETE на таблицы;
- target company для system_admin проверяется серверным разрешением и записывается в аудит;
- старые клиенты с прямым доступом блокируются minimum supported version и отзывом сессий.

Допустимая альтернатива без API: индивидуальная DB-идентичность каждого пользователя
и PostgreSQL RLS, опирающийся на неподменяемый current_user/session principal. Общая
DB-учётная запись и передаваемый actor_user_id для этой цели неприемлемы.

До появления доверенной границы фильтрация company_id защищает только от ошибок
приложения, но не от модифицированного или злонамеренного desktop-клиента. Такой
режим нельзя считать завершённой tenant-изоляцией.

Технический feature gate запрещает создание или активацию второй компании и вход её
пользователей до завершения cutover релиза 6 и успешного прохождения полной матрицы
migration/isolation/permission-тестов. Это ограничение нельзя заменять договорённостью
с оператором.


3. ЦЕЛЕВАЯ МОДЕЛЬ ДАННЫХ

3.1. Таблица companies

Рекомендуемые поля:
- id SERIAL PRIMARY KEY;
- name VARCHAR(255) NOT NULL;
- inn VARCHAR(12) NOT NULL;
- kpp VARCHAR(9) NULL;
- legal_address TEXT NULL;
- actual_address TEXT NULL;
- contact_email VARCHAR(255) NULL;
- website_url VARCHAR(500) NULL;
- status VARCHAR(20) NOT NULL DEFAULT 'active';
- task_catalog_version BIGINT NOT NULL DEFAULT 1;
- created_at TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP;
- updated_at TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP;
- archived_at TIMESTAMP NULL.

Ограничения:
- ИНН хранится строкой, а не числом;
- длина ИНН: 10 или 12 символов;
- КПП: 9 символов или NULL;
- email проверяется приложением и, по возможности, CHECK-ограничением;
- URL нормализуется приложением;
- уникальность рекомендуется задавать по паре (inn, kpp).

Причина уникальности (inn, kpp): одно юридическое лицо может иметь несколько
обособленных подразделений с одинаковым ИНН и разными КПП.

3.2. Изменения employees

Добавить:
- company_id INTEGER REFERENCES companies(id);
- role VARCHAR(50) NOT NULL DEFAULT 'employee';
- updated_at TIMESTAMP;
- blocked_at TIMESTAMP NULL (если такого состояния ещё нет).

Индексы:
- idx_employees_company_id;
- idx_employees_company_active по company_id и is_dismissed;
- индекс по role при необходимости административных выборок.

Ограничение первого этапа:
CHECK role IN ('employee', 'company_admin', 'system_admin').

3.3. Company ID в бизнес-сущностях

Добавить company_id минимум в:
- tasks;
- chats;
- stickies;
- task_statuses;
- task_tags;
- task_tags_link.

В дальнейшем добавить в:
- departments;
- positions;
- документы;
- проекты;
- шаблоны и справочники компании.

Почему company_id должен храниться непосредственно в tasks и chats:
- принадлежность данных не изменится после перевода автора в другую компанию;
- запросы проще и быстрее;
- легче создавать индексы и политики безопасности;
- снижается риск ошибочного JOIN через текущего сотрудника.

3.4. Чаты

Добавить chats.company_id NOT NULL после миграции данных.

Инварианты:
- создатель чата принадлежит chats.company_id;
- все chat_members принадлежат chats.company_id;
- личный чат создаётся только между сотрудниками одной компании;
- групповой чат содержит только сотрудников одной компании;
- сообщения наследуют границу доступа через chat_id.

На первом этапе messages.company_id можно не добавлять, если каждое чтение сообщения
обязательно проверяет принадлежность пользователя к чату и компании чата.
В будущем company_id в messages полезен для RLS, аудита и партиционирования.

3.5. Задачи

Добавить tasks.company_id NOT NULL после миграции данных.

Инварианты:
- автор, создатель и исполнитель задачи принадлежат tasks.company_id;
- наблюдатели принадлежат той же компании;
- комментарии доступны только участникам компании задачи;
- автоматические стикеры создаются только сотрудникам компании задачи.

3.6. Статусы задач и теги компании

Статусы задач и теги являются справочниками компании, а не глобальными справочниками.
Сотрудник видит и использует только статусы и теги своей компании.

Изменения task_statuses:
- добавить company_id INTEGER NOT NULL REFERENCES companies(id);
- запретить изменение company_id после создания записи;
- добавить is_active BOOLEAN NOT NULL DEFAULT TRUE;
- добавить is_initial BOOLEAN NOT NULL DEFAULT FALSE;
- добавить semantic_type VARCHAR(30) NOT NULL с допустимыми значениями
  new, in_progress, completed, cancelled;
- is_terminal вычислять из semantic_type либо защищать CHECK-ограничением от
  противоречивой комбинации значений;
- сохранить code, title, color и sort_order;
- уникальный индекс по (company_id, LOWER(BTRIM(code)));
- при необходимости уникальный индекс по (company_id, LOWER(BTRIM(title)));
- частичный UNIQUE INDEX по company_id WHERE is_initial=TRUE AND is_active=TRUE;
- не разрешать архивировать единственный активный начальный статус без атомарного
  назначения замены.

Изменения task_tags:
- добавить company_id INTEGER NOT NULL REFERENCES companies(id);
- запретить изменение company_id после создания записи;
- добавить is_active BOOLEAN NOT NULL DEFAULT TRUE;
- уникальный функциональный индекс по (company_id, LOWER(BTRIM(name)));
- одинаковое название тега разрешено в разных компаниях.

Нормализация code/title/name должна быть единой для индексов, поиска и ON CONFLICT:
предпочтительно использовать одну DB-функцию либо generated normalized_name/code.
Update API не принимает company_id, а изменение tenant-колонки дополнительно запрещается
column privileges и защитным trigger для task_statuses, task_tags и task_tags_link.

Изменения task_tags_link:
- добавить company_id NOT NULL;
- company_id связи должен совпадать с company_id задачи и тега;
- UNIQUE (task_id, tag_id) сохраняется;
- использовать составные внешние ключи, чтобы нельзя было привязать к задаче тег
  другой компании; триггер может только дополнять их понятным текстом ошибки.

Для составных внешних ключей потребуются уникальные ключи:
- tasks(company_id, id);
- task_statuses(company_id, id);
- task_tags(company_id, id).

Тогда допустимы ограничения:
- tasks(company_id, status_id) -> task_statuses(company_id, id) ON DELETE RESTRICT;
- task_tags_link(company_id, task_id) -> tasks(company_id, id) ON DELETE CASCADE;
- task_tags_link(company_id, tag_id) -> task_tags(company_id, id) ON DELETE RESTRICT.

После backfill tasks.status_id должен стать NOT NULL. Если клиент не передал status_id,
create_task выбирает активный is_initial статус компании текущего пользователя.
Статический глобальный DEFAULT status_id использовать нельзя.

Удалять используемые статусы и теги физически не следует.
Использовать is_active=FALSE: старые задачи сохраняют название и связь, но элемент
не предлагается при создании или редактировании новых задач.
Прикладной DB-роли запрещается DELETE из task_statuses и task_tags; физическое удаление
возможно только отдельной административной процедурой после проверки ссылок.

Автоматизация завершения задачи использует semantic_type='completed', а не is_terminal
и не отображаемое название. cancelled является терминальным состоянием, но не запускает
архивацию связанного стикера, если отдельное бизнес-правило не установлено явно.

При создании компании необходимо атомарно создавать стандартный набор статусов.
Рекомендуется хранить системный шаблон отдельно либо создавать набор в функции
provision_company_defaults(company_id). Изменения справочника одной компании не должны
изменять справочники уже созданных или других компаний.
Provisioning гарантирует ровно один активный is_initial статус. Стандартные теги
создаются только при наличии утверждённого шаблона; иначе новая компания начинает
с пустым собственным справочником тегов.

Управление справочниками:
- employee может просматривать активные статусы и теги своей компании;
- право создавать и редактировать статусы задаётся разрешением task_statuses.manage;
- право создавать и архивировать теги задаётся разрешением task_tags.manage;
- company_admin получает оба разрешения по умолчанию;
- system_admin действует только в явно выбранном контексте компании.

Изменение статуса или тега атомарно увеличивает task_catalog_version компании.
Клиентский кэш использует ключ company_id + task_catalog_version + session_generation;
перевод сотрудника между компаниями отзывает старую сессию и инвалидирует открытые формы.

3.7. Будущая ролевая модель

Поле employees.role допустимо как первый этап.
Целевая схема:
- roles(id, company_id, code, title, is_system);
- permissions(id, code, title);
- role_permissions(role_id, permission_id);
- employee_roles(employee_id, role_id).

Примеры разрешений:
- employees.view;
- employees.invite;
- employees.edit;
- employees.assign_role;
- tasks.view_all;
- tasks.create;
- tasks.delete;
- task_statuses.manage;
- task_tags.manage;
- chats.create_group;
- company.edit;
- audit.view.


4. ЭТАП 0. АУДИТ И ПОДГОТОВКА

Задачи:
1. Создать резервную копию рабочей БД.
2. Зафиксировать схему всех таблиц и внешних ключей.
3. Посчитать существующих сотрудников, задачи, чаты и участников чатов.
4. Найти задачи с отсутствующими авторами, исполнителями или создателями.
5. Найти чаты с некорректными участниками.
6. Проверить уникальность email и логинов.
7. Зафиксировать текущие сценарии авторизации, регистрации и восстановления пароля.
8. Добавить минимальные smoke-тесты до изменения поведения.

Артефакты:
- дамп БД;
- отчёт аудита;
- список аномальных записей;
- контрольные количества строк по таблицам;
- утверждённые решения из раздела 2.

Критерий завершения:
известно, как каждый существующий пользователь и объект получит компанию.


5. ЭТАП 1. БЕЗОПАСНАЯ МИГРАЦИЯ КОМПАНИЙ

Этап делится на два релизных подэтапа:
- 1A: companies, nullable company_id и backfill основных сущностей;
- 1B: отдельный cutover справочников после развёртывания tenant-aware функций,
  доверенной серверной сессии и блокировки старых клиентов.

Шаг 1. Создать таблицу companies без изменения текущих запросов.

Шаг 2. Создать компанию «Основная компания» для существующих данных.
Её реквизиты должны быть указаны оператором миграции, а не придуманы автоматически.

Шаг 3. Добавить nullable company_id в employees, tasks, chats, stickies,
task_statuses, task_tags и task_tags_link.

Шаг 4. Заполнить employees.company_id компанией по умолчанию.

Шаг 5. Заполнить:
- tasks.company_id по компании created_by или author_id;
- chats.company_id по компании created_by;
- stickies.company_id по компании user_id.

Шаг 5.1. Перенести глобальные статусы и теги в справочники компаний:
- до записи построить отчёт обо всём глобальном каталоге и его использовании задачами
  каждой компании;
- новые semantic_type и is_initial сначала добавить nullable, заполнить по утверждённой
  конфигурации и только после проверки установить NOT NULL/DEFAULT;
- утвердить явную mapping-конфигурацию old status code/id -> is_initial и semantic_type;
  неизвестную семантику выносить в отчёт и не определять по подстроке title;
- проверить legacy-поля tasks.status и tasks.status_id, отдельно зафиксировать записи
  только с одним значением, с конфликтом, NULL или ссылкой на отсутствующий статус;
- в maintenance-окне снять старые глобальные UNIQUE(name) и UNIQUE(code), затем создать
  company-scoped функциональные уникальные индексы;
- для каждой существующей компании перенести полный утверждённый активный каталог
  статусов и тегов, а не только значения, уже используемые её задачами;
- создать постоянные staging/mapping-таблицы миграции с PRIMARY KEY(old_id, company_id),
  UNIQUE(new_id), состоянием шага и идемпотентным ON CONFLICT;
- повторный запуск сначала использует существующий mapping и не создаёт новый клон;
- для valid tasks.status_id использовать mapping old_id + task.company_id;
- для задачи только с текстовым tasks.status выполнять утверждённое точное сопоставление
  normalized code/title внутри каталога компании;
- конфликт текста и ID, orphan status_id и неизвестное текстовое значение блокируют
  cutover до ручного решения; при обоих NULL is_initial назначается только по заранее
  утверждённой политике, иначе cutover также блокируется;
- сформировать отчёт old/new status для каждой исправленной задачи;
- одной транзакцией заполнить task_tags_link.company_id = tasks.company_id по task_id;
  связь без существующей задачи вынести в отчёт и не продолжать cutover;
- переназначить task_tags_link.tag_id по компании связанной задачи и проверить, что
  company_id link совпадает и с задачей, и с новым тегом;
- для основной компании допускается переиспользовать исходные строки с mapping на тот
  же id; при клонировании для всех компаний исходные строки удаляются только после
  проверки отсутствия ссылок либо переносятся в отдельный системный шаблон;
- для компании без утверждённого каталога создать стандартные статусы через
  provision_company_defaults(company_id), а теги оставить пустыми либо создать из
  отдельно утверждённого шаблона;
- прекратить двойную запись в legacy tasks.status; единственным источником истины после
  cutover становится tasks.status_id;
- проверить, что один новый статус или тег не используется задачами разных компаний.

Простое заполнение company_id в существующих строках task_statuses и task_tags
недопустимо: один глобальный статус или тег мог использоваться несколькими компаниями.
На время снятия глобальных ограничений, клонирования и переназначения приложение должно
быть полностью недоступно для чтения и записи задач и справочников. Read-only режима
недостаточно: старый запрос чтения может показать клоны нескольких компаний.
До установки NOT NULL не должно оставаться исходных строк с company_id IS NULL.

Шаг 6. Проверить отсутствие NULL и межкорпоративных связей, включая совпадение
company_id задачи, её статуса и каждого назначенного тега.

Шаг 7. Создать индексы и уникальные ключи, необходимые для составных внешних ключей.

Шаг 8. После проверки установить NOT NULL там, где это безопасно.

Шаг 9. Добавить внешние ключи и ограничения, включая:
- tasks(company_id, status_id) -> task_statuses(company_id, id) ON DELETE RESTRICT;
- task_tags_link(company_id, task_id) -> tasks(company_id, id) ON DELETE CASCADE;
- task_tags_link(company_id, tag_id) -> task_tags(company_id, id) ON DELETE RESTRICT;
- функциональную уникальность нормализованного code статуса внутри компании;
- уникальность нормализованного имени тега внутри компании.

Старые одиночные внешние ключи следует удалить либо привести к согласованному ON DELETE,
чтобы не оставлять дублирующие ограничения с разным поведением.

Миграция должна быть идемпотентной:
- ADD COLUMN IF NOT EXISTS;
- повторное выполнение не создаёт дубликатов;
- заполнение выполняется только для NULL;
- каждый шаг проверяет результат.
- staging/mapping-таблицы и состояние этапов сохраняются до истечения rollback-window.

Откат:
- до клонирования можно откатить приложение, сохранив неиспользуемые nullable-столбцы;
- во время клонирования откатывается транзакция либо восстанавливается дамп;
- после клонирования и до новых пользовательских записей возможен обратный remap через
  сохранённые mapping-таблицы и возврат прежних ограничений;
- после начала работы компаний предпочтителен forward-fix; восстановление дампа означает
  согласованную потерю данных после точки резервной копии согласно RPO;
- запуск старого клиента на схеме после клонирования запрещён version gate;
- mapping-таблицы удаляются только после окончания подтверждённого rollback-window.


6. ЭТАП 2. КОНТЕКСТ АВТОРИЗОВАННОГО ПОЛЬЗОВАТЕЛЯ

После входа user_data должен содержать:
- employee_id;
- full_name;
- company_id;
- company_name;
- role;
- is_dismissed / is_blocked.

Правила:
- заблокированная или архивная компания не может войти в систему;
- уволенный или заблокированный сотрудник не может войти;
- employee без company_id не допускается после завершения миграции;
- UI может использовать company_id для отображения, но не как источник доверия.

Создать единые функции:
- get_user_access_context(employee_id);
- get_employee_company_id(employee_id);
- require_same_company(actor_id, target_employee_id);
- require_company_role(actor_id, allowed_roles);

В серверном API employee_id для этих функций берётся из доверенного request/session
context. Значение actor_user_id, присланное клиентом как обычный параметр, игнорируется.

Не следует копировать проверки ролей вручную по десяткам функций.


7. ЭТАП 3. ЦЕНТРАЛИЗОВАННАЯ ИЗОЛЯЦИЯ ДАННЫХ

Главное правило:
любая функция чтения или изменения получает доверенный actor_user_id из серверной
сессии и проверяет его компанию. Для фоновой операции используется company-scoped
service principal/job context; глобальная задача без явного перебора tenant-ов запрещена.

Опасный вариант:
get_task_detail(task_id)

Целевой вариант:
get_task_detail(task_id, trusted_request_context)

SQL обязательно содержит условие company_id, полученное из доверенного request context.

Проверить и изменить группы функций:
- сотрудники;
- контакты;
- личные и групповые чаты;
- сообщения и вложения;
- задачи, комментарии и изображения;
- стикеры;
- уведомления;
- черновики;
- закреплённые чаты;
- поиск;
- пересылка сообщений.

Отдельно включить в реестр все функции справочников задач:
- получение, создание, изменение и архивирование статусов;
- получение, создание, изменение и архивирование тегов;
- get_status_by_id, get_status_by_code и get_tag_by_id;
- назначение и снятие тегов у задачи;
- переименование и слияние тегов;
- массовое изменение статуса и тегов;
- импорт, экспорт, автозаполнение и фоновые обработчики.

Чужой и несуществующий ID должны давать одинаковый внешний результат, например not found,
чтобы нельзя было определять существование объектов другой компании перебором ID.
Импорт разрешает статусы и теги по code/name только внутри job.company_id и не доверяет
внешним status_id/tag_id.

Особое внимание:
- запрос объекта непосредственно по ID;
- UPDATE и DELETE;
- массовые операции;
- фоновые таймеры;
- автоматическое создание стикеров;
- экспорт и вложения.

Критерий завершения:
знание ID объекта другой компании не позволяет прочитать или изменить объект.

9. ЭТАП 5. ОГРАНИЧЕНИЕ ЧАТОВ

Изменить:
- get_contacts_and_groups;
- get_employees;
- get_or_create_personal_chat;
- create_group_chat;
- добавление участника группы;
- получение сообщений;
- отправку и пересылку сообщений;
- уведомления;
- поиск чатов и сообщений.

Правила личного чата:
- оба сотрудника активны;
- оба принадлежат одной компании;
- повторный чат не создаётся;
- пользователь является участником чата.

Правила группового чата:
- creator.company_id = chat.company_id;
- каждый member.company_id = chat.company_id;
- добавление внешнего сотрудника отклоняется;
- после увольнения доступ участника прекращается согласно политике компании.

Миграционный риск:
существующий групповой чат может содержать сотрудников, которым назначили разные компании.
Такие чаты нельзя исправлять автоматически без отчёта и решения администратора.


10. ЭТАП 6. ОГРАНИЧЕНИЕ ЗАДАЧ

Изменить:
- get_tasks;
- get_task_detail;
- create_task;
- update_task;
- delete_task;
- get_all_statuses(actor_user_id);
- get_all_tags(actor_user_id);
- create_status(actor_user_id, ...);
- update_status(actor_user_id, status_id, ...);
- archive_status(actor_user_id, status_id);
- create_tag(actor_user_id, ...);
- update_tag(actor_user_id, tag_id, ...);
- archive_tag(actor_user_id, tag_id);
- комментарии;
- наблюдателей;
- селекторы исполнителей;
- автоматические стикеры;
- уведомления о задачах.

Правила:
- пользователь видит задачи только своей компании;
- исполнитель и наблюдатели выбираются только из своей компании;
- company_id задачи определяется серверной логикой по создателю;
- UI не передаёт доверенный company_id;
- перевод сотрудника не переносит исторические задачи;
- при увольнении активные задачи должны быть переназначены.
- пользователь видит и выбирает только активные статусы и теги своей компании;
- компания статуса, каждого тега, исполнителя и наблюдателя проверяется в одной
  транзакции создания или изменения задачи;
- status_id и tag_ids, переданные клиентом, считаются недоверенными;
- update API не принимает company_id справочника или задачи как изменяемое поле;
- завершённость задачи определяется semantic_type, а не сравнением отображаемого
  названия с текстом «Выполнена»; is_terminal не отличает completed от cancelled;
- использованный статус или тег архивируется через is_active=FALSE, а не удаляется;
- create_tag не использует глобальный ON CONFLICT(name): конфликт и обновление
  разрешаются только внутри company_id текущего пользователя.

Конкурентная целостность:
- выбранные строки статуса и тегов блокируются SELECT ... FOR UPDATE до commit;
- company_id и is_active проверяются после получения lock, поэтому параллельное
  архивирование не проходит между проверкой и записью задачи;
- tag_ids блокируются в стабильном порядке для снижения риска deadlock;
- при deadlock/serialization failure операция безопасно повторяется ограниченное число раз;
- массовая операция сначала разрешает весь набор задач и справочников, сравнивает число
  разрешённых ID с запрошенным и только затем изменяет данные одной транзакцией;
- чужой, несуществующий или неактивный ID откатывает весь batch, частичный успех запрещён;
- affected_count после записи обязан совпасть с количеством запрошенных объектов.

Необходимо определить видимость внутри компании:
- все сотрудники видят все задачи компании;
- либо только автор, исполнитель, наблюдатели и руководители.

Текущее требование предполагает первый вариант: все задачи компании видимы всем сотрудникам.
Рекомендуется предусмотреть настройку company.tasks_visibility для будущего ограничения.

12. ЭТАП 8. ТЕСТИРОВАНИЕ

12.1. Миграционные тесты
- чистая БД;
- копия старой БД;
- повторный запуск миграции;
- прерывание между этапами;
- отсутствие company_id после заполнения;
- совпадение количества сотрудников, задач и чатов до и после;
- клонирование одного глобального статуса для задач компаний A и B;
- клонирование одного глобального тега для задач компаний A и B;
- корректность таблиц соответствия старых и новых ID;
- сохранение статуса и тегов каждой задачи после переназначения;
- контрольная сумма связей task_tags_link до и после переназначения;
- отсутствие task_statuses, task_tags и task_tags_link без company_id;
- невозможность добавить составные внешние ключи при искусственно созданной
  межкорпоративной ссылке;
- повторный запуск после частично завершённого клонирования использует сохранённый mapping
  и не создаёт повторные клоны;
- снятие глобальных UNIQUE выполняется до вставки одинаковых каталогов компаний;
- исходные глобальные строки не остаются с company_id IS NULL перед NOT NULL;
- tasks.status и tasks.status_id проверяются для случаев: только одно поле, конфликт,
  оба NULL и ссылка на отсутствующий статус;
- после cutover единственным источником истины является tasks.status_id;
- нормализация считает «Баг», «баг» и « Баг » одним тегом внутри компании;
- сохраняются is_active, semantic_type, is_initial, color и sort_order;
- provision_company_defaults полностью откатывается при сбое в середине;
- новая компания получает независимый начальный статус и не изменяет чужой каталог;
- проверяется допустимая длительность блокировок maintenance-окна;
- обратный remap через mapping-таблицы восстанавливает исходные ID и связи;
- backup восстанавливается с совпадением checksum и успешными smoke-тестами;
- сбой при установке FK/NOT NULL оставляет БД в документированном восстанавливаемом
  состоянии и повторный запуск корректно продолжает этап.

12.2. Тесты изоляции
Создать компании A и B, пользователей A1, A2 и B1.

Проверить:
- A1 видит A2, но не B1;
- A1 не создаёт чат с B1;
- A1 не добавляет B1 в группу;
- A1 не читает чат B по известному chat_id;
- A1 не читает задачу B по известному task_id;
- A1 не изменяет и не удаляет задачу B;
- A1 не получает вложения и уведомления B;
- поиск не возвращает данные B;
- автоматический стик не создаётся пользователю другой компании;
- A1 видит статусы и теги A, но не видит справочники B;
- A1 не создаёт и не изменяет статус или тег компании B по известному ID;
- A1 не назначает задаче A статус или тег компании B;
- одинаковые code статуса и имя тега разрешены одновременно в A и B;
- архивный статус или тег остаётся у старой задачи, но не предлагается для новой;
- массовые операции, импорт, поиск и автозаполнение не возвращают справочники B.
- поддельный actor_user_id B в физической сессии A не меняет доверенный principal;
- чужой и несуществующий ID возвращают одинаковую внешнюю ошибку;
- фоновая задача и импорт в контексте A полностью отклоняют status_id/tag_id компании B.

12.3. Тесты ролей
- employee не меняет роли;
- company_admin управляет только своей компанией;
- company_admin не назначает system_admin;
- system_admin выполняет только явно разрешённые глобальные действия;
- employee просматривает справочники своей компании, но не управляет ими без права;
- company_admin управляет статусами и тегами только своей компании;
- system_admin перед управлением справочником явно выбирает компанию.

12.4. UI-тесты
- пункт «Сотрудники» расположен правильно;
- список и поиск работают;
- недоступные действия скрыты;
- переключение страниц не раскрывает старые данные;
- после смены пользователя кэши очищены;
- фоновые таймеры используют контекст текущего пользователя;
- селекторы статусов и тегов показывают только значения текущей компании;
- после смены пользователя справочники предыдущей компании очищены из моделей и кэша;
- открытая форма компании A после входа пользователя B инвалидируется и не сохраняет данные;
- кэш справочников имеет ключ company_id + catalog_version + session_generation;
- неактивные статусы и теги не предлагаются при создании задачи;
- существующая задача корректно показывает свой неактивный статус или тег.

12.5. Негативные тесты
- подмена employee_id;
- подмена company_id;
- прямой вызов UPDATE/DELETE чужого объекта;
- удалённый сотрудник;
- заблокированная компания;
- отсутствующая компания;
- межкорпоративный список member_ids;
- гонка при переводе или увольнении сотрудника;
- подмена status_id или tag_ids на ID другой компании;
- глобальный ON CONFLICT по имени тега;
- изменение company_id существующего статуса или тега;
- физическое удаление справочника, который используется задачей;
- DELETE использованного и неиспользованного справочника прикладной ролью запрещён;
- параллельное архивирование статуса и создание задачи с этим статусом;
- конкурентное создание одинакового нормализованного тега создаёт одну запись;
- mixed-company batch полностью откатывается и не изменяет разрешённую часть;
- affected_count массовой операции совпадает с requested_count;
- completed с произвольным title запускает автоматизацию, cancelled не запускает её,
  а title «Выполнена» без semantic_type=completed не считается завершением;
- архивный статус можно заменить в старой задаче, но нельзя назначить новой;
- смена company_id справочника блокируется API, правами и ограничением БД;
- system_admin без разрешения и server-side target context не меняет справочник;
- deadlock/serialization failure приводит к ограниченному безопасному retry;
- desktop DB-role получает permission denied на прямой SELECT/INSERT/UPDATE/DELETE;
- клиент ниже minimum version не входит, а ранее открытая старая сессия теряет доступ;
- feature gate не позволяет активировать вторую компанию до успешного релиза 6.


13. ЭТАП 9. РАЗВЁРТЫВАНИЕ

Рекомендуемая последовательность:
1. Резервная копия БД.
2. Развёртывание nullable-столбцов и companies.
3. Заполнение company_id существующих данных.
4. Развёртывание минимального серверного API/доверенной сессии либо защищённых
   EXECUTE-функций, покрывающих все существующие операции приложения; feature gate
   второй компании остаётся закрытым.
5. Включение minimum supported client version, отзыв старых сессий и только после
   покрытия всех операций отзыв прямых table grants у desktop-роли.
6. Полная остановка чтения и записи задач и справочников на maintenance-окно.
7. Активация tenant-aware функций релиза 5 и проверок недоверенных ID без допуска
   пользовательского трафика до полного завершения релиза 6.
8. Снятие глобальных UNIQUE, клонирование статусов и тегов и переназначение ссылок.
9. Автоматические проверки целостности, checksum и контрольные выборки.
10. Установка NOT NULL, составных внешних ключей и уникальных ограничений.
11. Возврат приложения из maintenance и наблюдение за ошибками.
12. Включение страницы «Сотрудники».
13. Удаление временного совместимого кода и mapping-таблиц только после стабилизации
    и истечения согласованного rollback-window.

Не следует одновременно выполнять миграцию, включать строгие ограничения и удалять
старую логику в одном необратимом релизе.

Pre-open go/no-go условия перед возвратом приложения:
- контрольные количества и checksum совпадают с утверждённым отчётом;
- ноль NULL и tenant mismatch в обязательных связях;
- все составные FK и проверки запрета чужих ID проходят;
- старые клиенты и сессии отсутствуют;
- desktop DB-role получает permission denied на прямые SELECT/INSERT/UPDATE/DELETE;
- полный набор migration/isolation/permission-тестов прошёл на staging-копии;
- maintenance уложился в согласованное окно либо принят явный план продления;
- проверены RTO/RPO резервной копии и назначен ответственный за решение об откате;
- только после выполнения этих условий открывается feature gate второй компании.

Post-open observation gate:
- установлены длительность наблюдения и ответственный дежурный;
- контролируются ошибки, отказы доступа, latency и число tenant mismatch;
- пороги для автоматического закрытия трафика, rollback или forward-fix утверждены заранее;
- mapping-таблицы и резервная копия не удаляются до завершения окна наблюдения и отката.


14. НАБЛЮДАЕМОСТЬ И АУДИТ

Добавить структурированные журналы:
- actor_user_id;
- company_id;
- операция;
- тип и ID объекта;
- результат;
- время;
- причина отказа.

Создать audit_log для критичных действий:
- создание и изменение компании;
- приглашение и увольнение;
- изменение роли;
- удаление задачи;
- создание, изменение и архивирование статуса или тега;
- изменение semantic_type, is_initial и порядка статусов;
- переименование и слияние тегов;
- создание группового чата;
- массовый экспорт;
- попытка доступа к чужой компании.

Для отказанного cross-tenant обращения журнал содержит actor company, тип и ID целевого
объекта и причину отказа, но клиенту не раскрывается факт существования чужого объекта.

Не записывать в обычные логи пароли, токены, полный текст сообщений и чувствительные данные.


15. ПРОИЗВОДИТЕЛЬНОСТЬ

Обязательные индексы:
- employees(company_id, is_dismissed);
- tasks(company_id, updated_at);
- tasks(company_id, status_id);
- chats(company_id);
- stickies(company_id, user_id, is_hidden, is_archived);
- UNIQUE task_statuses(company_id, id);
- уникальный функциональный индекс task_statuses(company_id, lower(btrim(code)));
- частичный UNIQUE task_statuses(company_id) WHERE is_initial AND is_active;
- INDEX task_statuses(company_id, is_active, sort_order);
- UNIQUE task_tags(company_id, id);
- уникальный функциональный индекс task_tags(company_id, lower(btrim(name)));
- частичный INDEX task_tags(company_id, lower(btrim(name))) WHERE is_active;
- UNIQUE task_tags_link(task_id, tag_id);
- INDEX task_tags_link(company_id, task_id);
- покрывающий INDEX task_tags_link(company_id, tag_id, task_id);
- составные индексы таблиц участников по employee_id и chat_id.

Все списки должны иметь:
- серверную пагинацию;
- ограниченный размер результата;
- стабильную сортировку;
- поиск с подходящими индексами при росте объёма.

Фоновые polling-таймеры создают линейную нагрузку с ростом числа клиентов.
Среднесрочная цель: события через серверный API и WebSocket/уведомления.


16. КЛЮЧЕВЫЕ РИСКИ И МЕРЫ

Риск: данные другой компании видны через старую функцию.
Мера: реестр всех операций, доверенный principal из серверной сессии, tenant-фильтр
и интеграционные тесты прямого доступа по известному ID.

Риск: desktop-клиент использует общие реквизиты PostgreSQL.
Мера: не включать мультикомпании до минимального API либо индивидуальной DB-идентичности
с RLS; отозвать прямые table grants и заблокировать старые клиенты.

Риск: пользователь подменяет передаваемый company_id.
Мера: вычислять company_id по авторизованному пользователю.

Риск: существующие межкорпоративные связи.
Мера: отчёт до миграции и ручное решение конфликтов.

Риск: перевод сотрудника меняет историю.
Мера: неизменяемый company_id на задачах и чатах.

Риск: удаление компании каскадно удаляет данные.
Мера: мягкая блокировка компании и явная процедура удаления.

Риск: role превращается в множество if/else.
Мера: ограниченный набор ролей сейчас и переход к permissions позже.

Риск: кэш предыдущего пользователя остаётся в UI.
Мера: ключ company_id + catalog_version + session_generation, очистка моделей и
инвалидация всех ранее открытых форм при logout или переводе сотрудника.

Риск: фоновые процессы работают после смены пользователя.
Мера: привязать таймеры к сессии и останавливать при logout.

Риск: company_admin получает слишком широкие права.
Мера: явная матрица разрешений и аудит действий.

Риск: старый глобальный статус или тег используется задачами нескольких компаний.
Мера: клонировать справочники для каждой компании и переназначать ссылки через
проверяемые mapping-таблицы, а не назначать исходной строке одну компанию.

Риск: старый или частично обновлённый клиент показывает дубликаты либо чужие
статусы и теги.
Мера: сначала выпустить совместимое чтение с обязательной фильтрацией company_id,
затем переносить данные; неподдерживаемые версии клиента блокировать на входе.

Риск: create_tag с глобальным ON CONFLICT(name) изменяет тег другой компании.
Мера: уникальность и обработка конфликта только по company_id и нормализованному имени.

Риск: между проверкой статуса/тегов и сохранением задачи справочник архивируется
или меняет компанию.
Мера: блокировать выбранные строки до commit, обрабатывать deadlock/retry; company_id
справочника неизменяем, межкорпоративные ссылки блокируются составными внешними ключами.

Риск: массовая операция молча пропускает чужие или отсутствующие ID и частично
изменяет разрешённые объекты.
Мера: сначала разрешить весь набор, сравнить requested_count/allowed_count, затем
изменить одной транзакцией и проверить affected_count; при расхождении полный rollback.

18. КРИТЕРИИ ГОТОВНОСТИ ПЕРВОГО ЭТАПА МУЛЬТИКОМПАНИЙ

Релиз считается готовым, если:
- каждый активный сотрудник связан с компанией;
- каждая задача и чат связаны с компанией;
- каждый статус и тег связан ровно с одной компанией;
- каждая связь задачи со статусом или тегом находится внутри одной компании;
- пользователь видит только сотрудников своей компании;
- нельзя создать личный или групповой чат с другой компанией;
- нельзя получить чужой чат или сообщение по известному ID;
- пользователь видит только задачи своей компании;
- нельзя получить или изменить чужую задачу по известному ID;
- селекторы исполнителей и наблюдателей ограничены компанией;
- селекторы статусов и тегов ограничены компанией;
- нельзя получить, изменить или назначить статус либо тег другой компании по ID;
- одинаковые названия тегов и коды статусов не конфликтуют между компаниями;
- у каждой компании ровно один активный начальный статус;
- автоматизация completed/cancelled не зависит от отображаемого названия статуса;
- нет операций справочников без доверенного principal и обязательного tenant-фильтра;
- отсутствуют глобальные выборки и глобальный ON CONFLICT(name/code);
- desktop-клиент не имеет общих прямых table grants к PostgreSQL;
- роли employee/company_admin/system_admin проверяются на уровне операций;
- миграция повторно выполняется без повреждения данных;
- mapping-таблицы и резервная копия сохраняются весь rollback-window;
- сценарий отката отрепетирован и уложился в утверждённые RTO/RPO;
- тесты изоляции компаний проходят автоматически;
- административные действия записываются в аудит.


19. РЕКОМЕНДУЕМАЯ ОЧЕРЁДНОСТЬ РЕЛИЗОВ

Релиз 1: схема companies, nullable company_id и аудит старых данных и справочников.
Релиз 2: минимальный серверный API/доверенный principal, расширенный контекст
авторизации и перенос операций с прямого SQL на API либо защищённые EXECUTE-функции.
Релиз 3: изоляция сотрудников и страница «Сотрудники».
Релиз 4: изоляция чатов и сообщений.
Релиз 5: подготовка tenant-aware функций задач, статусов и тегов, проверок недоверенных
ID, minimum client version и механизма блокировки старых сессий.
Релиз 6: единый maintenance/cutover: активация релиза 5 без промежуточного трафика,
отзыв прямых table grants, клонирование справочников, remap ID, составные FK и включение
полной изоляции задач, комментариев, вложений и стикеров.
Релиз 7: приглашения и управление сотрудниками.
Релиз 8: аудит и усиление ролевой модели.
Релиз 9: расширение серверного API, усиление RLS и событийная синхронизация.

Каждый релиз должен иметь собственную миграцию, тесты, резервную копию,
критерии приёмки и описанный план отката.

Релиз 5 можно подготовить заранее, но его tenant-aware режим активируется только вместе
с релизом 6 в одном maintenance-окне. Между активацией новых функций и завершением remap
пользовательский трафик запрещён. Feature gate второй компании открывается последним.


20. ИТОГОВАЯ РЕКОМЕНДАЦИЯ

Начинать следует не со страницы «Сотрудники», а с безопасной модели company_id,
миграции существующих данных и централизованной проверки доступа. После этого UI,
чаты и задачи можно подключать поэтапно без риска, что визуальная фильтрация создаст
ложное ощущение изоляции.

До подключения второй компании desktop-клиент должен лишиться общих полномочий прямого
доступа к PostgreSQL. Минимальный серверный API либо индивидуальная DB-идентичность с RLS
являются обязательной технической границей. Долгосрочно API и RLS расширяются так, чтобы
ошибка интерфейса или изменённый клиент не могли раскрыть данные другой компании.
